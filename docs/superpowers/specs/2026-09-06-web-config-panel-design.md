# طرح: پنل وب تنظیم و راه‌اندازی تونل

**تاریخ:** ۶ سپتامبر ۲۰۲۶ · **وضعیت:** طرح تأییدشده، پیش از پیاده‌سازی

## مسئله

پنل فعلی (`web/`) فقط **می‌خواند**: سه منبع `/stats`، `/data` و `panel.json` را
poll می‌کند و نشان می‌دهد. هر تغییری در تونل — نصب، توکن، transport، پورت‌ها،
فعال‌سازی سرویس — از راه SSH و `farshub` انجام می‌شود.

هدف این طرح: همان پنل بتواند تونل را **کانفیگ کند و بالا بیاورد**، از سرور خام
تا تونل زنده، بدون اینکه CLI کارایی‌اش را از دست بدهد.

سه قید که همه‌ی تصمیم‌ها را شکل داده‌اند:

1. **تونل زنده است و کاربر متصل دارد.** هیچ تغییری نباید ناخواسته قطعی بسازد.
2. **CLI سرجایش می‌ماند.** کاربر باید بتواند هر کدام را انتخاب کند؛ پنل جانشین
   CLI نیست، مصرف‌کننده‌ی آن است.
3. **هر پنل فقط سمت خودش را تنظیم می‌کند.** بدون مدیریت از راه دور، بدون
   ارتباط پنل‌به‌پنل.

## بخش ۱ — معماری و مرزها

```
مرورگر ──► nginx :8088 ──┬──► فایل‌های ایستا  /var/lib/farshub/web
         (auth_basic)     ├──► /stats, /data   → 127.0.0.1:2060  (موتور اجرا)
                          └──► /api/*          → 127.0.0.1:2061  (farshub-api)
                                                      │
                                                      └─ sudo farshub <زیردستور>
```

سه جزء، سه مرز صریح:

**nginx :8088** — همان چیزی که `panel-up` امروز می‌سازد. یک لایه‌ی احراز هویت
برای هر سه مسیر. `/api/` فقط یک `location` تازه در همان server block است، پس
پنل و API هرگز دو رمز جدا نمی‌گیرند.

**موتور اجرا `127.0.0.1:2060`** — دست‌نخورده. `/stats` و `/data` مثل امروز.

**`farshub-api` روی `127.0.0.1:2061`** — سرویس systemd تازه، Python از کتابخانه‌ی
استاندارد (روی سرور 3.12.3 موجود است، پس هیچ وابستگی‌ای نصب نمی‌شود)، با کاربر
غیرروت `farshub-api` که shell ندارد.

### مرز اصلی: CLI تنها نویسنده‌ی کانفیگ است

`farshub-api` **هرگز** TOML نمی‌نویسد و **هرگز** `systemctl` صدا نمی‌زند. هر
کاری که root می‌خواهد از `sudo farshub <زیردستور>` می‌گذرد.

این تصمیم مهم‌ترین بخش طرح است. اگر API خودش می‌نوشت، دو نویسنده‌ی مستقل روی یک
فایل داشتیم و واگرایی پنل و CLI فقط با نظم نگه داشته می‌شد. با این مرز، واگرایی
**ساختاراً ناممکن** است: هر چه پنل می‌کند دقیقاً همان است که CLI می‌کند، چون
همان کد است.

sudoers با آرگومان‌های ثابت — نه wildcard، نه `tee`:

```sudoers
farshub-api ALL=(root) NOPASSWD: /usr/local/bin/farshub install server, \
  /usr/local/bin/farshub install client, \
  /usr/local/bin/farshub apply-config server, \
  /usr/local/bin/farshub apply-config client, \
  /usr/local/bin/farshub start server, /usr/local/bin/farshub start client, \
  /usr/local/bin/farshub stop server, /usr/local/bin/farshub stop client, \
  /usr/local/bin/farshub restart server, /usr/local/bin/farshub restart client, \
  /usr/local/bin/farshub enable server, /usr/local/bin/farshub enable client, \
  /usr/local/bin/farshub disable server, /usr/local/bin/farshub disable client, \
  /usr/local/bin/farshub config server, /usr/local/bin/farshub config client, \
  /usr/local/bin/farshub logs server -n [0-9]*, \
  /usr/local/bin/farshub logs client -n [0-9]*, \
  /usr/local/bin/farshub token
```

دو ورودی آخرِ فهرست برای **خواندن**‌اند، نه نوشتن — دلیلش در بخش ۲. الگوی
`-n [0-9]*` تنها جایی است که آرگومان کاملاً ثابت نیست، و به ارقام محدود شده تا
`-f` (لاگ زنده، که هرگز تمام نمی‌شود) از آن رد نشود.

اجازه دادن به `tee /etc/farshub/*` یعنی نوشتن محتوای دلخواه در مسیر دلخواه —
کاربر غیرروت اسماً غیرروت می‌شد. به همین دلیل زیردستور `apply-config` وجود دارد
(بخش ۳).

**دامنه‌ی خرابی یک باگ در backend:** یک کانفیگ FarsHub خراب، به‌علاوه‌ی یک
ری‌استارت سرویس. برگشت‌پذیر و محدود — نه کل ماشین.

### راه‌اندازی روی سرور خام

```bash
sudo ./bin/farshub setup
```

نه `curl | sh`. پروژه‌ای که هش باینری‌اش را تبلیغ می‌کند نباید کاربر را به
اجرای اسکریپت دیده‌نشده عادت بدهد.

## بخش ۲ — سطح API

هشت اندپوینت زیر `/api/`. JSON در، JSON بیرون. قالب `/stats` و `/data` عوض
نمی‌شود، پس پنل پایش بی‌تغییر کار می‌کند.

| متد | مسیر | کار |
| --- | --- | --- |
| `GET` | `/api/state` | نصب شده؟ کدام سمت؟ سرویس فعال؟ توکن برنمی‌گردد |
| `GET` | `/api/config` | کانفیگ فعلی به JSON، توکن ماسک‌شده |
| `PUT` | `/api/config` | مقادیر تازه → stdin `farshub apply-config` |
| `POST` | `/api/install` | `{side}` → `farshub install <side>` |
| `POST` | `/api/service` | `{action}` از `start|stop|restart|enable|disable` |
| `POST` | `/api/token` | توکن ۳۲ بایتی تازه می‌سازد و برمی‌گرداند (نمی‌نویسدش) |
| `GET` | `/api/logs?n=100` | آخرین خطوط journal، با فیلتر برندینگ |
| `GET` | `/api/preflight` | پیش از ذخیره: پورت اشغال؟ TLS لازم و غایب؟ |

### نوشتن atomic است، و اعتبارسنجی کار خودمان است

`apply-config` روی فایل موقت می‌نویسد، اعتبارسنجی می‌کند، بعد `mv` می‌کند —
جایگزینی در همان filesystem اتمیک است، پس هیچ‌وقت کانفیگ نیم‌نوشته روی دیسک
نمی‌ماند. پشتیبان قبلی هم می‌ماند (`server.toml.bak`)، پس اگر تغییری تونل را
خواباند برگشت یک دستور است.

**موتور اجرا حالت اعتبارسنجی ندارد.** فقط `-c`/`-config` می‌گیرد و با آن تونل
را واقعاً بالا می‌آورد — روی سرور زنده یعنی دو نمونه که سر یک پورت دعوا می‌کنند.
پس اعتبارسنجی کاملاً در `apply-config` انجام می‌شود: allowlist کلیدها، نوع و
بازه‌ی هر مقدار، و قالب `bind_addr` / `remote_addr` / ردیف‌های `ports`. فهرست
کلیدها بسته است چون در موتور کامپایل شده و تغییر نمی‌کند.

نتیجه‌ی عملی: یک کانفیگ نامعتبر **پیش از** نوشتن رد می‌شود، نه بعد از ری‌استارت.

### ری‌استارت هرگز خودکار نیست

ذخیره‌ی کانفیگ سرویس را ری‌استارت نمی‌کند. پنل نوار زرد نشان می‌دهد:
«تغییرها ذخیره شد — برای اعمال، ری‌استارت لازم است» با دکمه‌ی کنارش.

دلیل: کاربر متصل وجود دارد و یک ری‌استارت ناخواسته یعنی قطعی برای همه. تصمیمِ
قطع کردن باید صریح و آگاهانه باشد.

### خواندن هم از CLI می‌گذرد، نه فقط نوشتن

کانفیگ `600` و مالکش root است — عمدی، چون توکن داخلش است و
[CLI.md](../../CLI.md#check-چه-چیزی-را-میسنجد) دسترسی بازتر را «خطا» می‌شمارد. پس
کاربر غیرروت `farshub-api` **نمی‌تواند مستقیم بخواندش**، و `GET /api/config` هم
باید از `sudo farshub config <سمت>` بگذرد که خودش توکن را ماسک می‌کند.

همین برای `GET /api/logs`: خواندن journal عضویت در گروه `systemd-journal`
می‌خواهد. به‌جای دادن آن عضویت، از `sudo farshub logs` استفاده می‌شود که فیلتر
برندینگ را هم اعمال می‌کند.

پس دو ورودی دیگر به sudoers اضافه می‌شود (`config` و `logs`، هر دو سمت). این
دقیقاً همان جهت‌گیری بخش ۱ است: CLI تنها راه، برای خواندن هم مثل نوشتن. و مزیت
جانبی‌اش این است که ماسک‌کردن توکن در یک جا انجام می‌شود، نه دو جا.

### توکن یک‌طرفه است

`GET /api/config` مقدار توکن را `********` می‌دهد. فیلد خالی در فرم یعنی
«عوضش نکن». پس توکن از سرور به مرورگر **هیچ‌وقت** نمی‌رود و اسکرین‌شات پنل
لو نمی‌دهد — همان قاعده‌ای که `farshub config` و `farshub status` رعایت می‌کنند.

## بخش ۳ — تغییرهای CLI

سه زیردستور تازه در `bin/farshub`، هر سه با ارزش مستقل از پنل.

### `apply-config <سمت>`

JSON از stdin، اعتبارسنجی، نوشتن atomic روی TOML موجود. کامنت‌های انتهای خط
دست‌نخورده می‌مانند (بر پایه‌ی `set_conf_val` فعلی).

بدون این زیردستور، sudoers باید `tee /etc/farshub/*` را اجازه بدهد. برای
اسکریپت‌نویسی هم مستقلاً به کار می‌آید:

```bash
echo '{"transport":"wssmux"}' | sudo farshub apply-config server
```

### `api-up` / `api-down`

سرویس `farshub-api`، کاربرش، فایل sudoers و قاعده‌ی `location /api/` را
نصب/حذف می‌کند. دقیقاً الگوی `panel-up`/`panel-down` که کار کرده و مستند است —
از جمله idempotent بودن و برگرداندن کامل.

### `setup`

`install` + `panel-up` + `api-up`، و چاپ آدرس و رمز پنل. چیز تازه‌ای نمی‌کند،
سه دستور را یکی می‌کند تا سرور خام با یک خط به تونل زنده برسد.

### دو تغییر کوچک در کد موجود

`panel-up` اگر سرویس API نصب باشد قاعده‌ی `location /api/` را از اول می‌نویسد،
تا ترتیب اجرای `panel-up` و `api-up` مهم نباشد.

و `SITE_NAME` که امروز هاردکد است، با متغیر محیطی قابل override می‌شود
(`FARSHUB_SITE_NAME`) — دلیلش در بخش ۶.

## بخش ۴ — رابط کاربری

پنل امروز یک صفحه است. دو تب بالا می‌آید: **پایش** (همان چیز فعلی، بی‌تغییر) و
**تنظیمات**. تب با hash عوض می‌شود (`#/settings`)، پس refresh و bookmark کار
می‌کند و هیچ router کتابخانه‌ای لازم نیست.

بدون فریم‌ورک، بدون build step، بدون CDN — قید سخت پروژه. همه‌ی رشته‌ها با
`data-i18n` و در هر دو زبان، با همان کلیدهای نقطه‌دار تخت `i18n.js`. توکن‌های
`--petrol-*` / `--mint-*` / `--amber-400` بازاستفاده می‌شوند و `letter-spacing`
همچنان فقط زیر `[data-locale='en']` می‌ماند.

### چهار کارت در تب تنظیمات

**سرویس** — وضعیت و چهار دکمه. `restart`، `stop` و `disable` دیالوگ تأیید
می‌خواهند و `aria-describedby` دارند که می‌گوید «همه‌ی اتصال‌های فعلی قطع
می‌شوند».

**تونل** — `transport` (با هشدار «رمزنگاری ندارد» روی گزینه‌های ناامن)،
`bind_addr` یا `remote_addr` بسته به سمت، و `token` با دکمه‌ی «تولید» و
«رونوشت». زیرش یادآوری که باید در دو طرف عیناً یکسان باشد.

**پورت‌ها** — فقط سمت server (کلاینت `ports` ندارد). ردیف‌های قابل
افزودن/حذف، هر ردیف یکی از قالب‌های `443` یا `8443=443` یا `2000-2100`.
اعتبارسنجی همان لحظه در مرورگر و **دوباره** سمت سرور.

**پیشرفته** — mux، بافرها، `sniffer`، `log_level`، `pprof`. پیش‌فرض بسته
(`<details>`) با یک خط: «این مقادیر باید در دو طرف هم‌خوان باشند؛ بدون دلیل
عوضشان نکنید.»

### ویزارد سرور خام

اگر `/api/state` بگوید نصب نیست، به‌جای تب‌ها یک ویزارد سه‌مرحله‌ای می‌آید:
انتخاب سمت → مقادیر پایه → بازبینی و نصب.

## بخش ۵ — امنیت

| خطر | مهار |
| --- | --- |
| API روی اینترنت | `127.0.0.1:2061` — nginx تنها راه، `auth_basic` سرجایش |
| CSRF | چک `Origin` روی هر متد نوشتاری؛ نبودن یا نخواندنش ⇒ رد |
| تزریق فرمان | آرگومان هرگز از رشته ساخته نمی‌شود؛ `subprocess` با آرایه، `shell=False` |
| مقدار مخرب در TOML | اعتبارسنجی allowlist سمت root: هر کلید یک نوع و یک بازه |
| کلید ناشناس | رد می‌شود — کلیدهای TOML در موتور کامپایل شده‌اند، فهرست بسته است |
| بالا رفتن دسترسی | کاربر بدون shell (`/usr/sbin/nologin`)، sudoers با آرگومان ثابت |
| سخت‌سازی سرویس | `NoNewPrivileges`، `ProtectSystem=strict`، `PrivateTmp`، `MemoryMax=128M` |
| DoS با ری‌استارت پیاپی | حداکثر یک عمل نوشتاری در هر ۳ ثانیه |

دو چیز که این طرح **حل نمی‌کند** و باید دانست: ارتباط همچنان HTTP است پس رمز
`auth_basic` رمزنگاری‌نشده رد می‌شود (راه‌حل: TLS یا تونل SSH، همان توصیه‌ی
فعلی [PANEL.md](../../PANEL.md))، و `bind_addr` تونل allowlist ندارد.

## بخش ۶ — تست روی سرور، بدون لمس تونل زنده

`farshub` متغیرهای محیطی prefix را می‌پذیرد، پس انزوا واقعی است نه امیدوارانه:

```
/opt/fh-test/{conf,libexec,state,log}     ← FARSHUB_*
farshub-test-server.service               ← یونیت جدا
تونل تست  :3990    موتور تست :2062    API تست :2063    nginx تست :8099
تونل زنده :3080    موتور     :2060    API     :2061    nginx     :8088  ← دست نمی‌خورد
```

تست اصلی، **سرور خام**: با `FARSHUB_CONF_DIR` خالی `setup` زده می‌شود و کل
ویزارد از راه API پیش می‌رود، تا یک تونل تست بین **دو** نمونه‌ی جدا (`server` و
`client`) روی همان ماشین برقرار شود — چون هر پنل فقط سمت خودش را تنظیم می‌کند و
هر دو مسیر باید سنجیده شوند.

یک نکته که اگر دیده نشود تونل زنده را می‌خواباند: **نام سایت nginx در
`bin/farshub` هاردکد است** — `SITE_NAME='farshub-panel'` (خط ۶۱۸)، و هفت جای
دیگر از همان یک متغیر می‌خوانند. اجرای `panel-up` در تست، سایت زنده را بازنویسی
می‌کرد.

پس `SITE_NAME` باید قابل override با متغیر محیطی شود، همان‌طور که بقیه‌ی
`FARSHUB_*` هستند:

```sh
SITE_NAME=${FARSHUB_SITE_NAME:-farshub-panel}
```

یک خط تغییر، و از آن به بعد `FARSHUB_SITE_NAME=farshub-test` نمونه‌ی تست را
کاملاً جدا می‌کند — بدون آن، انزوای بخش ۶ نصفه است. `nginx -t` هم پیش از هر
`reload` اجرا می‌شود، همان کاری که `panel-up` امروز می‌کند.

پایان کار: پاک‌سازی کامل نمونه‌های تست، و تأیید اینکه `farshub-server` و `nginx`
در تمام مدت `active` مانده‌اند و PID موتور زنده عوض نشده است.

## آنچه بیرون از دامنه است

- مدیریت از راه دور یا پنل‌به‌پنل (تصمیم صریح: هر پنل فقط سمت خودش)
- TLS خودکار / Let's Encrypt
- چند کاربر با نقش‌های متفاوت — `auth_basic` تک‌لایه کافی است
- ویرایش `bin/farshub-core` یا هر تغییری که MD5 آن را عوض کند
