# دستور `farshub`

`bin/farshub` یک اسکریپت POSIX sh است — تنها چیزی که کاربر تایپ می‌کند. موتور
اجرا `farshub-core` است (build آپ‌استریم، **دست‌نخورده**) و این پوسته آن را صدا
می‌زند.

هدف: کاربر در همه‌ی دستورها و خروجی‌ها فقط FarsHub را ببیند، بدون یک بایت
تغییر در موتور اجرا.

## چرا اسکریپت، نه ویرایش باینری

موتور اجرا `stripped` است و سورسش در این مخزن نیست. رشته‌های داخلی
(«Backhaul Premium»، لینک `t.me/dawsh42`) فقط با ویرایش hex عوض می‌شوند که
offsetها را می‌شکند. پس هیچ‌کدام تغییر نکرده‌اند و MD5 موتور اجرا همان
`2f86ffb6ab33de43abfc606e12a8d972` است. جزئیات در [ORIGIN.md](ORIGIN.md).

## پیدا کردن موتور اجرا

به‌ترتیب گشته می‌شود و اولین مورد اجرایی برنده است:

1. `$FARSHUB_CORE` (مسیر کامل)
2. `$FARSHUB_LIBEXEC/farshub-core` — پیش‌فرض `/usr/local/libexec/farshub`
3. `farshub-core` کنار خود اسکریپت — برای اجرا از مخزن باز‌نشده
4. `$FARSHUB_BIN_DIR/farshub-core`
5. `farshub-core` در `PATH`

اگر هیچ‌کدام نبود، خطای «موتور اجرا پیدا نشد» می‌دهد.

## دستورها

| دستور | کار |
| --- | --- |
| `install <سمت>` | نصب موتور، کانفیگ و یونیت systemd |
| `run <سمت>` | اجرای مستقیم در ترمینال، با فیلتر برندینگ |
| `start` / `stop` / `restart` | کنترل سرویس |
| `enable` / `disable` | اجرای خودکار در boot + راه‌اندازی / لغو و توقف |
| `status [سمت]` | وضعیت سرویس و خلاصه‌ی کانفیگ |
| `logs [سمت] [-f] [-n N]` | رویدادها از journal؛ پیش‌فرض ۵۰ خط |
| `config [سمت]` | نمایش کانفیگ با توکن ماسک‌شده |
| `edit [سمت]` | باز کردن کانفیگ در `$EDITOR` |
| `token` | توکن تصادفی ۳۲ بایتی |
| `check [سمت]` | بررسی سلامت نصب و هشدارهای امنیتی |
| `panel-up [سمت]` | بالا آوردن پنل: nginx + رمز + فایروال + `panel.json` |
| `panel-down` | برگرداندن همه‌ی تغییرهای `panel-up` |
| `panel` | توضیح پنل وب و گزینه‌هایش |
| `panel-meta [سمت]` | `panel.json` پنل را روی stdout می‌سازد |
| `paths [سمت]` | همه‌ی مسیرها و نام‌های این نصب را چاپ می‌کند |
| `version` | نسخه‌ی CLI و موتور اجرا |
| `support` | لینک تلگرام پشتیبانی |
| `help` | راهنما |

هر دستور ناشناخته‌ی دیگری عیناً به موتور اجرا پاس داده می‌شود، پس فراخوانی
قدیمی `farshub -c /etc/farshub/server.toml` هم کار می‌کند.

### «سمت» و حدس زدنش

`server` پورت‌ها را Listen می‌کند، `client` همیشه Dial می‌کند (تونل معکوس).
`s` و `c` هم پذیرفته می‌شود.

اگر سمت را ننویسید، از روی کانفیگ‌های نصب‌شده حدس زده می‌شود: اگر فقط یکی از
`server.toml`/`client.toml` باشد همان برداشته می‌شود؛ اگر هر دو باشند خطا
می‌دهد و صریح بودن می‌خواهد؛ اگر هیچ‌کدام نباشد به `install` ارجاع می‌دهد.

## فیلتر برندینگ

خروجی موتور اجرا از `sed` عبور می‌کند:

```
Backhaul Premium    → FarsHub Tunnel
backhaul / Backhaul → FarsHub
t.me/dawsh42        → t.me/vpsfa
```

دو چیز عمداً **بازنویسی نمی‌شوند**، چون برندینگ نیستند و عوض کردنشان کاربر را
گمراه می‌کند:

| رشته | چرا حفظ می‌شود |
| --- | --- |
| `backhaul.json` | نام فایل پیش‌فرض لاگ sniffer — یک مسیر واقعی روی دیسک |
| `github.com/musix/backhaul` | مسیر پکیج در stack trace — برای جست‌وجوی خطا لازم است |

هر دو اول به یک نشانه‌ی موقت تبدیل و در آخر برگردانده می‌شوند.

فیلتر روی `run` و `logs` و پاس‌دادن دستور ناشناخته اعمال می‌شود. `-u` در `sed`
یک بار سنجیده می‌شود؛ اگر پشتیبانی شود لاگ زنده بافر نمی‌شود.

## چرا `_exec` در یونیت systemd

یونیت‌ها `farshub _exec <سمت>` را صدا می‌زنند، نه `farshub run`. تفاوت:

- `_exec` هیچ pipe ندارد و با `exec` جای همین پروسه را می‌گیرد، پس systemd
  خودِ موتور اجرا را می‌بیند و کد خروج و سیگنال‌ها (`SIGTERM` هنگام
  `systemctl stop`) دست‌نخورده می‌مانند. فیلتر برندینگ اعمال نمی‌شود چون
  `farshub logs` هنگام **خواندن** فیلتر می‌کند.
- `run` برای ترمینال است: فیلتر دارد، و چون pipe کد خروج را می‌خورد (POSIX sh
  `PIPESTATUS` ندارد) کد خروج موتور از یک فایل موقت برگردانده می‌شود — بدون
  آن عیب‌یابی بی‌فایده است.

یونیت‌ها `SyslogIdentifier=farshub` دارند، وگرنه بعد از `exec` نام موتور اجرا
در journal ظاهر می‌شود.

## `check` چه چیزی را می‌سنجد

هشدارهای امنیتی مستند در README را روی نصب واقعی می‌سنجد، نه به‌عنوان توصیه:

| بررسی | نتیجه |
| --- | --- |
| وجود موتور اجرا و کانفیگ | خطا اگر نباشد |
| دسترسی کانفیگ ≠ `600`/`400` | خطا — توکن قابل خواندن است |
| `token = "CHANGE_ME"` | خطا |
| `pprof = true` | خطا — `0.0.0.0:6060` بدون auth |
| `transport` بدون رمزنگاری | هشدار — `wss`/`wssmux` پیشنهاد می‌شود |
| `web_port ≠ 0` | هشدار — مگر اینکه drop-in فایروالِ `panel-up` سر جایش باشد |
| `log_level = "info"` | هشدار — توکن در خطای mismatch لاگ می‌شود |
| نبودن یونیت systemd | هشدار |

کد خروج با وجود «خطا» غیرصفر می‌شود (هشدارها صفر می‌مانند)، پس در اسکریپت
قابل استفاده است.

## توکن هرگز چاپ نمی‌شود

`status` مقدار `token` را در خلاصه نمی‌آورد و `config` آن را با `********`
جایگزین می‌کند — تا در paste و اسکرین‌شات لو نرود. برای دیدن مقدار واقعی
فایل کانفیگ را مستقیم بخوانید.

## `install` و پنل وب

`install` علاوه بر موتور، کانفیگ و یونیت، پوشه‌ی `web/` را هم در
`$FARSHUB_STATE_DIR/web` می‌گذارد و کنارش `panel.json` می‌سازد. دو نکته:

- **کانفیگ دست‌نخورده می‌ماند، پنل نه.** فایل‌های پنل کد هستند، پس هر بار
  بازنویسی می‌شوند. چیزی که خودتان به آن پوشه اضافه کرده‌اید حذف نمی‌شود
  (`cp -R`، نه `rsync --delete`). `devserver.py` عمداً کنار گذاشته می‌شود؛ هرگز
  نباید سرو شود.
- **`panel.json` هر بار از نو ساخته می‌شود** با نقشِ همان سمتی که نصب می‌کنید.
  اگر بعداً نقش را دستی عوض کردید یا فایل را از دست دادید، `panel-meta`
  همان را روی stdout می‌دهد:

```bash
farshub panel-meta server > /var/lib/farshub/web/panel.json
```

محتوایش فقط چیزهایی است که موتور اجرا **گزارش نمی‌کند**: نقش (`server`/`client`)،
نسخه، و نام میزبان/IP/سیستم‌عامل/کرنل/معماری/تعداد هسته. هر فقره‌ای که روی آن
ماشین خوانده نشود نوشته نمی‌شود، و `bind` فقط سمت server می‌آید. بدون این فایل
پنل «سمت اجرا نامعلوم» نشان می‌دهد — تفصیل در [PANEL.md](PANEL.md).

## `panel-up` چه چیزهایی را عوض می‌کند

`install` فایل‌های پنل را روی دیسک می‌گذارد ولی چیزی آن‌ها را سرو نمی‌کند.
`panel-up` بقیه‌ی کار را می‌کند و — این مهم است — **بیرون از پوشه‌های خود
FarsHub هم مینویسد**. فهرست کامل، تا بدانید `panel-down` چه چیزی را برمی‌گرداند:

| مسیر | کار | `panel-down` |
| --- | --- | --- |
| `/etc/farshub/<سمت>.toml` | `web_port` (و با `--sniffer` مقدار `sniffer`) | `web_port = 0` |
| `/etc/systemd/system/farshub-<سمت>.service.d/10-firewall.conf` | قاعده‌ی DROP روی `web_port` | حذف می‌شود |
| `/etc/nginx/sites-available/farshub-panel` (یا `conf.d/farshub-panel.conf`) | سایت پنل | حذف می‌شود |
| `/etc/nginx/sites-enabled/farshub-panel` | لینک فعال‌سازی | حذف می‌شود |
| `/etc/nginx/farshub.htpasswd` | رمز `auth_basic` | حذف می‌شود |
| `/etc/nginx/sites-enabled/default` | فقط اگر nginx را همین دستور نصب کرده باشد، لینکش برداشته می‌شود | برنمی‌گردد |
| `/var/lib/farshub/web/panel.json` | از نو ساخته می‌شود | می‌ماند |
| `/var/lib/farshub/panel.conf` | حالت، تا `panel-down` بداند چه چیزی را برگرداند | حذف می‌شود |
| بسته‌ی `nginx` | اگر نبود نصب می‌شود | **حذف نمی‌شود** |
| قاعده‌ی `ufw` روی پورت پنل | فقط اگر ufw فعال باشد | بسته می‌شود |

سه تصمیم که ممکن است غیرشهودی باشند:

- **قاعده‌ی فایروال روی سرویس سوار است، نه در `iptables-save`.** با
  `ExecStartPost`/`ExecStopPost` دقیقاً تا وقتی موتور گوش می‌دهد اعمال است و در
  هر boot از نو ساخته می‌شود، پس به `netfilter-persistent` وابسته نیست و
  فایل یونیت shipped هم دست‌نخورده می‌ماند. اگر `iptables` خراب باشد سرویس بالا
  **نمی‌آید** — عمدی است: تونلِ خوابیده بهتر از پنلِ بی‌رمزِ باز روی اینترنت است.
- **رمز با `openssl passwd -apr1` ساخته می‌شود، نه `htpasswd`.** روی نصب معمولی
  `apache2-utils` نیست و نصبش برای یک خط hash زیادی است.
- **اجرای دوباره رمز را نمی‌چرخاند.** وگرنه هر بار `panel-up` دسترسی کسی را
  قطع می‌کرد. برای رمز دلخواه `--password PASS` و برای رمز تصادفیِ تازه
  `--new-password`.
- **عوض کردن `--user` کاربر قبلی را حذف نمی‌کند.** خط قبلی در `htpasswd`
  می‌ماند و آن کاربر همچنان وارد می‌شود، پس `panel-up` نامش را چاپ می‌کند. حذف
  دستی است: خط را از `/etc/nginx/farshub.htpasswd` بردارید.

`--password` دو نویسه را نمی‌پذیرد: `:` (جداکننده‌ی خط `htpasswd`) و `'`. کمتر
از ۶ نویسه هم رد می‌شود. هر دو **پیش از** `need_root` سنجیده می‌شوند تا خطای
تایپی با `sudo` دوباره تکرار نشود.

`farshub panel` فقط توضیح می‌دهد و هیچ گزینه‌ای نمی‌گیرد؛ اگر گزینه بدهید با
کد ۲ و همان دستور درستِ `panel-up` جواب می‌دهد، چون بی‌صدا خوردنِ `--password`
یعنی کاربر فکر کند رمز عوض شد و نشده باشد.

اگر `nginx -t` کانفیگ را نپذیرد، سایت به حالت قبلش برمی‌گردد و دستور با خطا
تمام می‌شود — nginx زنده شکسته نمی‌شود.

## متغیرهای محیطی

برای تست نصب در یک prefix موقت، بدون دست زدن به سیستم:

| متغیر | پیش‌فرض |
| --- | --- |
| `FARSHUB_CORE` | — (مسیر کامل موتور اجرا) |
| `FARSHUB_LIBEXEC` | `/usr/local/libexec/farshub` |
| `FARSHUB_BIN_DIR` | `/usr/local/bin` |
| `FARSHUB_CONF_DIR` | `/etc/farshub` |
| `FARSHUB_UNIT_DIR` | `/etc/systemd/system` |
| `FARSHUB_LOG_DIR` | `/var/log/farshub` |
| `FARSHUB_STATE_DIR` | `/var/lib/farshub` |
| `FARSHUB_UNIT_PREFIX` | `farshub` — پیشوند نام یونیت systemd (`farshub-server.service`) |
| `FARSHUB_SITE_NAME` | `farshub-panel` — نام سایت nginx پنل |
| `FARSHUB_HTPASSWD` | `/etc/nginx/farshub.htpasswd` — فایل رمز پنل |

```bash
FARSHUB_CONF_DIR=/tmp/t/conf FARSHUB_LIBEXEC=/tmp/t/libexec ./bin/farshub install server
```

نصب در مسیرهای پیش‌فرض root می‌خواهد؛ نصب در یک prefix شخصی نه — فقط دسترسی
نوشتن سنجیده می‌شود.

سه تای آخر برای **انزوا** هستند. با آنها می‌توان یک نصب کامل و جدا روی همان
ماشین بالا آورد بدون اینکه نصب زنده لمس شود — نه سایت nginx‌اش بازنویسی شود و
نه `systemctl restart` سرویس زنده را بگیرد. `farshub paths` نشان می‌دهد هر
override به چه مسیری رسیده است:

```bash
FARSHUB_CONF_DIR=/opt/fh-test/conf FARSHUB_UNIT_PREFIX=farshub-test farshub paths server
```
